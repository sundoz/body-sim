# Ведение pull request в body-sim

Это симулятор заживления раны: непрерывная модель на сетке, параметры которой
откалиброваны по литературе. Из-за этого «красный тест» здесь значит не то же,
что в обычном сервисе, — см. раздел «Что означает упавший тест».

## Перед каждым пушем

Полный набор, который гоняет CI, воспроизводится локально за пару минут:

```bash
cargo fmt --all --check                      # < 1 с
cargo clippy --all-targets -- -D warnings    # < 1 с после прогрева, иначе ~30 с
cargo test --lib --bins                      # ~2 с, 71 модульный тест
cargo test                                   # ~110 с, все 92 теста
```

Первые три обязательны всегда. Полный `cargo test` обязателен, если тронуты
`src/params.rs`, `src/sim.rs`, `src/tissue.rs`, `src/therapy.rs` или
`src/simulation.rs`: только он гоняет клиническую регрессию и сверку с литературой,
а они идут ~95 и ~15 секунд соответственно. Это не зависание — не прерывай прогон.

Правки, меняющие поведение модели, дополнительно стоит прогнать вручную:

```bash
cargo run --release --bin body-sim -- --scenario necrotizing --days 20 --no-map
cargo run --release --bin body-sim -- --depth 9 --days 60 --no-map
```

`[profile.test] opt-level = 3` в `Cargo.toml` стоит именно ради скорости тестов —
не убирай его, иначе `cargo test` растянется на десятки минут.

## Устройство CI

| Джоба | Что делает |
|---|---|
| `Test (ubuntu-latest)` | fmt → clippy → `cargo build --release --all-targets` → `cargo test` |
| `Test (windows-latest)` | то же без fmt и clippy (они привязаны к Linux, чтобы не дублировать) |
| `Coverage` | `cargo llvm-cov --release --lib --bins` — только модульные тесты |
| `GitGuardian Security Checks` | внешняя проверка на секреты |

`Coverage` намеренно не гоняет `tests/` — клиническая регрессия под инструментированием
идёт слишком долго, а её полный прогон уже есть в `Test`. Не «чини» покрытие, добавляя
туда интеграционные тесты.

GUI (`src/bin/gui/`) собирается в CI, но его отрисовка не тестируется: нужен GPU.
Тесты в этих модулях покрывают только чистые функции — геометрию, шум, палитру, профайлер.

## Что означает упавший тест

Прежде чем править код, определи категорию — от неё зависит правильное действие.

**1. `tests/literature.rs` — параметры разошлись с литературой.**
Тест проверяет, что `Params::default` воспроизводит калибровочные ориентиры
(пики клеток, сроки эпителизации, прочность рубца) в пределах 1.25 допуска.
Если он покраснел после правки модели, это значит, что изменилась динамика,
а параметры остались от прежней. Правильное действие — перекалибровать:

```bash
cargo run --release --bin calibrate          # ~15 мин на все этапы
cargo run --release --bin calibrate 60 3     # только 3-й этап
```

и перенести напечатанные значения в `Params::default`, а таблицу «До калибровки / После»
в README — привести в соответствие. **Никогда не подгоняй значения в `Params::default`
вручную, чтобы тест позеленел**: они получены оптимизацией, а не подбором на глаз.

**2. `tests/clinical.rs` — модель перестала воспроизводить известный исход.**
Пороги там намеренно широкие: проверяется качественное поведение (ранняя хирургия
лечит, поздняя нет; отбор устойчивости при длинном курсе β-лактама), а не точные числа.
Поэтому такой провал — почти всегда настоящий регресс в диффе, а не хрупкий тест.
**Никогда не расширяй допуск и не смягчай порог, чтобы получить зелёный**;
если ты уверен, что новое поведение правильнее старого, меняй ожидание вместе
с обоснованием в сообщении коммита и в README, где эти исходы перечислены таблицей.

**3. Модульные тесты** — обычные тесты, чини как всегда.

## Инварианты, которые нельзя ломать

- **Детерминизм.** `parallel_step_is_deterministic` требует, чтобы результат не зависел
  от числа потоков. Блоки в `sim::step` не пересекаются и не сводятся редукцией —
  сохраняй это свойство. Проверка вручную:
  ```bash
  for n in 1 4; do RAYON_NUM_THREADS=$n ./target/release/body-sim --days 20 --every 1 --no-map | md5sum; done
  ```
  (нужен предварительный `cargo build --release --bin body-sim`).
  Никогда не «чини» детерминизм, убирая параллелизм: на 4 ядрах он даёт ~2.4×.
- **Устойчивость явной схемы.** `explicit_scheme_is_stable` держит `D · dt ≤ 0.25`.
  Поднимая любой коэффициент диффузии или `dt`, проверь этот запас.
- **Физичность полей.** `fields_stay_physical_during_infected_healing` следит, что
  плотности остаются в 0..1, `slough ≤ depth ≤ depth_max ≤ max_depth_mm` и нигде
  нет NaN. Новое поле добавляй в этот тест.
- **`unsafe` в проекте нет** — так и должно остаться.

## Конвенции

- Комментарии, докстринги, сообщения об ошибках и текст интерфейса — по-русски;
  идентификаторы — по-английски. Сообщения коммитов и описания PR — по-английски.
- `rustfmt.toml` задаёт 120 колонок: формулы модели и таблицы параметров не должны
  рваться. Не форматируй файл в другом стиле «заодно».
- Комментарий объясняет физиологию или причину выбора константы, а не синтаксис.
  Магическое число в модели без комментария о том, откуда оно, — повод его добавить.
- Ядро (`src/`) не знает о macroquad; всё, что про отрисовку, живёт в `src/bin/gui/`.
  Не тащи зависимость от графики в библиотеку.

## Что обновлять вместе с кодом

README содержит конкретные числа, и они устаревают молча:

- таблицы «Результаты», «Сценарии без лечения», «Антисептики», «Антибиотики» —
  если изменилось поведение модели;
- таблицу калибровки — если перекалибровал;
- число тестов в разделе «Тесты» — если добавил или убрал;
- список опций, если тронул разбор аргументов в `src/main.rs` (там же `HELP`).

Скриншоты `docs/screenshot-*.png` пересоздаются так:

```bash
cargo run --release -- --scenario necrotizing --depth 5 --days 3 --screenshot docs/screenshot-necrotizing.png
```

Это `default-run`, то есть GUI: команде нужен дисплей и GPU, в headless-окружении
и в CI она не отработает. Обновляй скриншоты только когда картинка действительно
перестала соответствовать описанию: это бинарные файлы, они раздувают историю.
